## Service placement and DAG groups

Use a proposed versioned placement record with exact identifiers:

```json
{
  "serviceId": "stable-cooker-service-id",
  "environmentId": "stable-environment-id",
  "destinationId": "configured-target-id",
  "provider": "vercel",
  "providerAccountId": "exact-owner-id",
  "providerProjectId": "exact-project-id",
  "providerDeploymentId": "exact-deployment-id",
  "region": "observed-or-unavailable",
  "runId": "source-run-id",
  "stageId": "source-stage-id",
  "artifactIdentity": "immutable-source-or-artifact-id",
  "observedAt": "successful-observation-time",
  "coverage": "explicit-scope"
}
```

This is a **design proposal**, not a currently supported API payload. Group by **environment → destination → service**, with stable identity instead of display names. A group may contain build/check/review/deploy nodes and show the resulting runtime only when a real receipt binds it. Configured intent, provider acceptance, ready state and ongoing health are separate observations.

Collapse/expand must preserve branches, joins, external ports and selected details. Distinguish successful-task, startup-readiness and runtime-traffic edges. Keyboard Step list and phone navigation remain available. A literal kitchen walking aisle can loop without implying a dependency cycle.

Current Compose Apps still select one compute target. A topology view containing several destinations is not permission to dispatch one Compose stack across targets. A future mixed-target planner must reject incompatible storage, networking and secret assumptions before accepting a deployment.

## Node/group inspector

| Tab | Required content and boundary |
|---|---|
| Placement | Exact configured/observed target, environment, provider resource and immutable deployment receipt |
| Runs | Recorded attempts/stages, approvals and artifact/source identities; no inferred live state |
| Logs | Stage/build logs separately from application runtime logs, correct deployment/replica, bounded time/lines/bytes, redaction and scoped export |
| Metrics | Actual provider-exposed request/error/duration or CPU/RAM/restart measurements with range/resolution/coverage/retention; unsupported is not zero |
| Storage | Exact volume/Drive/snapshot binding, region/mount/access mode and retention; no filesystem durability inferred from a path |
| Actions | Capability- and role-gated refresh, then separately verified promote/rollback/restart/retention operations |

Use immutable historical attribution. An externally changed or deleted resource must appear as drift/stale/unavailable rather than silently attaching a previous run to a newer deployment. Group aggregation must retain each service's coverage and permissions; it cannot turn partial observations into a healthy badge.

## Sandbox and persistent disk design

Vercel currently documents persistent Sandbox filesystem sessions and separate Sandbox Drives. Those are **platform offerings**, not current Cooker support. A stopped sandbox's persisted filesystem does not mean its processes remain running; resume startup and replay boundaries need explicit tests. Drives, filesystem snapshots, object storage and databases have different ownership, sharing and durability contracts.

Cooker should expose only capabilities qualified for the selected account/region/provider. For untrusted jobs, start with deny-all or narrow declared egress and supported credential brokering, pin source/image identity and bound resource/time/cost. Record actual command exit and uncertain provider replies. Stop and verify owned runs promptly; persistent state follows an explicit retention policy rather than being deleted with the process.

Durable storage needs versioned bindings, provider-supported access-mode/region rules, protected single-writer ownership where required, synthetic data hashes across stop/resume/redeploy and reviewed backup/restore. Do not offer ordinary Function scratch space as persistent disk. Do not automatically provision a Drive, database, public sandbox port or monitoring drain as part of the static landing/example release.
