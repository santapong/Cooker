## Detailed findings

### 1. Data race: RunPipeline writes the 202 response from the same *PipelineRun the spawned executor goroutine is mutating

- **Severity / Dimension:** high / concurrency
- **Location:** `backend/internal/handler/pipeline.go:389`
- **Tracking:** new
- **Evidence:** SpawnWithDeadline(ctx, run.ID, ..., func(ctx){ runCopy := run; h.Executor.Execute(ctx, p, runCopy) ... }) then line 398 `c.JSON(http.StatusAccepted, run)` — runCopy is a pointer alias, so the request goroutine JSON-encodes `run` while the spawned goroutine writes run.Status/run.StartedAt (executor.go:651-659) and appends to run.StageRuns[i].Artifacts (executor.go:1038). No happens-before between the `go func` and the c.JSON; concurrent append can realloc the slice mid-encode (torn read / encoder panic). This is the default inline path (jobqueue off), hit on every pipeline trigger; go test -race in CI will flag it.
- **Fix sketch:** In backend/internal/handler/pipeline.go RunPipeline: before SpawnWithDeadline, take a response snapshot the goroutine won't touch — e.g. respond with the pending run captured pre-spawn (clone the struct AND its StageRuns slice, since a shallow *run still aliases the StageRuns backing array that executor.go:606 writes into), then c.JSON the snapshot while Execute mutates the original; mirrors the durable path's intent of returning the pending run without sharing the pointer (no new package needed).
- **Why it is real (verifier):** Reproduced in backend/internal/handler/pipeline.go. run is a *model.PipelineRun (line 318); runCopy := run (390) is a pointer alias, not a copy. SpawnWithDeadline (server/runs.go:85-130) runs work in a separate `go func`, where Execute writes run.Status (executor.go:651), run.StartedAt (659), and appends into run.StageRuns[i].Artifacts via stageRunMap[...] = &run.StageRuns[i] (executor.go:606) → sr.Artifacts append (executor.go:1038). Meanwhile the request goroutine reflect-walks the SAME pointer at pipeline.go:398 `c.JSON(http.StatusAccepted, run)`. Nothing establishes happens-before between the goroutine spawn and the c.JSON, so this is a genuine concurrent read/write data race: torn read of the StartedAt pointer or a slice realloc mid-encode (encoder panic / partial body). It is the default path because the inline branch is gated by `h.Enqueuer == nil` (jobqueue off is the documented default), so it fires on every pipeline trigger and go test -race will flag it. stillOpen=true: not on the known-false-positive list (AES-GCM secrets, webhook FullName, wsHub launch order, SIGTERM nil srv.Close, kubectl sha); chain-recheck.md T6 only joined the heartbeat goroutine in runs.go (B.1.4) and B.8.2/"newly introduced #3" concern the separate *model.Pipeline definition pointer, not the *model.PipelineRun being encoded; remediation-plan T6's race-fix file list does not include this handler→encoder aliasing. Severity high not critical: it crashes/corrupts the 202 response under race but the run still executes and there is no security/data-loss impact.

### 2. executePush comment promises automatic prior-stage image resolution that the code never implements; canonical build→push pushes an empty source

- **Severity / Dimension:** high / correctness
- **Location:** `backend/internal/service/executor.go:1213`
- **Tracking:** new
- **Evidence:** Comment says "Source image: pick the first artifact produced by an earlier stage if none is explicitly set on the push stage" but the next line is just `source := stage.Config.Image` (1215) with no artifact fallback; `req := pusher.Request{Source: source, ...}` (1236) then sends "" to Crane.Push, where `name.ParseReference("")` fails. A build→push pipeline built in the UI (which only collects a push repository/registry, not an image) pushes an empty source and the stage fails; the Noop pusher hides this in tests.
- **Fix sketch:** In executePush (backend/internal/service/executor.go:1215), when stage.Config.Image == "", default source to the nearest upstream build stage's resolved image ref — reuse the existing buildplan.OutputResolver / deriveBuildOutputs (add an `image` output alongside digest/tag) so the push stage auto-resolves the prior build like the comment promises; and surface a push "Source image" field in frontend NodeConfigPanel.tsx (push case, ~line 154) for explicit overrides.
- **Why it is real (verifier):** Reproduced in the cited file. backend/internal/service/executor.go:1213-1215: the comment "pick the first artifact produced by an earlier stage if none is explicitly set" is immediately followed by `source := stage.Config.Image` with no fallback; line 1236 builds `pusher.Request{Source: source, ...}`. No automatic prior-stage resolution exists anywhere: executeBuild (1037-1050) only appends to its own sr.Artifacts and exposes digest/tag/tags outputs — it never writes the push stage's Config.Image; no handler-layer auto-injection exists (grep over internal/handler found only unrelated template stage-ID remapping). interpolateStageConfig does interpolate `image` (executor.go:306) but only from explicit ${stages.*} tokens a user must hand-author. The UI confirms the trigger: NodeConfigPanel.tsx push case (154-173) collects only registry+repository — no image/source field and no auto-wiring — and the build case (90-141) collects no Tags at all, so even the manual ${stages.build.tag} escape hatch resolves empty. With a real pusher (Crane is the default-case fallthrough in selectPusher, server.go:973-981 returns Crane for "crane"), Crane.Push calls name.ParseReference("") which returns ErrUnavailable (crane.go:53-55); DockerSock skips tagging then pushes an untagged target (docker.go:37-42). Noop (noop.go) ignores Source and returns a fake digest, which is exactly why tests pass. NOT closed: chain-recheck.md mentions push only for timeouts/rate-limits (B.3.5/B.3.7/B.6.7); remediation-plan.md has zero matches; 2026-06-full-audit.md line 98 catalogues a different push bug (crane.go:82 post-push digest empty). NOT on the known-false-positive list. Severity high (not critical): the canonical UI build→push pipeline cannot push for any operator running a real pusher backend, but it fails loud (stage error) not silently, is functional not security, and the out-of-box/dev/UAT default pusher is Noop so it doesn't bite the default config — it bites every production deployment that sets COOKER_PUSHER_BACKEND=crane|docker.

### 3. Mid-run progress persistence (RunUpdater) is wired only in tests, never in production — a crash mid-run loses every stage transition

- **Severity / Dimension:** high / correctness
- **Location:** `backend/internal/server/server.go:265`
- **Tracking:** new
- **Evidence:** The production `service.NewExecutor(...)` call (server.go:265-282) lists WithBuilder/WithPusher/WithLogBroadcaster/etc. but NOT WithRunUpdater; `rg -l WithRunUpdater` matches only executor.go (def) + executor_test.go. So `e.runUpdater == nil` and `persistProgress` (executor.go:979-986) returns immediately, making the entire drain/batch goroutine (executor.go:842-914) a no-op in prod. The only prod write is the single `h.Store.Runs.Update` AFTER Execute returns (pipeline.go:392). dag-performance.md item #10 and chain-recheck claim this is "Closed (debounced drain writes mid-run)" — it is not; a crash relies solely on the boot orphan sweep marking the whole run failed.
- **Fix sketch:** In backend/internal/server/server.go add `service.WithRunUpdater(st.Runs.Update)` to the NewExecutor option list at :265-282, mirroring the already-wired store-backed callbacks (WithLogStore/WithStatusBroadcaster); existing drain machinery in executor.go then persists mid-run unchanged.
- **Why it is real (verifier):** Reproduced in cited code. server.go:265-282 builds the production Executor with WithBuilder/Pusher/Deployer/DockerDeployer/ComposeDeployer/StageRunner/StageApprovals/LogBroadcaster/LogStore/StatusBroadcaster/DeployGovernanceHook — but NOT WithRunUpdater. Grep confirms WithRunUpdater is referenced only in executor.go (def at :498) and executor_test.go (:713,:773); no non-test caller exists. So e.runUpdater is nil in prod, and persistProgress (executor.go:979-986) returns immediately at the `if e.runUpdater == nil { return }` guard, making the entire debounced drain goroutine (executor.go:861-909) a no-op — every batched/eager flush calls persistProgress, which does nothing. The only production write of run state is the single h.Store.Runs.Update AFTER Execute returns at internal/handler/pipeline.go:392 (the finding's "pipeline.go:392" — service/pipeline.go is only 175 lines, so it is the handler file, and the line matches exactly). A crash mid-run therefore leaves the row status='running' until the boot-time SweepOrphans (postgres/run.go:196) blanket-marks it status='failed', error='orphaned: heartbeat stale at boot' — no per-stage progress is recovered. dag-performance.md item #10 marks this "Closed — a debounced drain goroutine ... now writes at most once per min(500ms,10 transitions)"; the drain code did land but is inert in prod, so the Closed claim is false. chain-recheck.md does not list this as reopened, and it is not on the known-false-positive list (AES-GCM secrets / webhook FullName / wsHub launch order / SIGTERM nil srv.Close / kubectl sha — none apply). Severity: high — a fully shipped, test-passing feature is silently dead in production and the audit docs assert the opposite, masking the gap; bounded below critical because it loses granular stage progress, not the run itself or service availability (orphan sweep still fails the run cleanly).

### 4. Durable job queue has no stale-`running` reaper: a crashed/OOM-killed worker permanently wedges the pipeline's concurrency key

- **Severity / Dimension:** high / reliability
- **Location:** `backend/internal/jobqueue/postgres.go:114-184`
- **Tracking:** new
- **Evidence:** Dequeue commits the tx that sets status='running', locked_by=<worker> (no DB lock held after commit); the concurrency gate is `NOT EXISTS (... j2.status='running' AND j2.concurrency_key=...)`, and ConcurrencyKey is `"pipeline:"+pipelineID` (enqueuer.go:41). Nothing ever resets a stale `running` row by locked_at age — `Reschedule/Fail` all require `locked_by=$2`, so only the owning (now-dead) worker could clear it. The `locked_at` column exists in migration 010 but is never read back.
- **Fix sketch:** In backend/internal/jobqueue/postgres.go add a Reap(ctx, olderThan) method (and a goroutine started from jobqueue_boot.go like the Pool) that runs UPDATE jobs SET status='pending', locked_by='', locked_at=NULL, started_at=NULL WHERE status='running' AND locked_at < NOW() - $interval, mirroring the existing per-call NOW()/locked_at pattern already in Dequeue/Reschedule; back it with a partial index on (status, locked_at) via a new migration alongside migration 010.
- **Why it is real (verifier):** Reproduced in backend/internal/jobqueue/postgres.go:114-184. Dequeue's CTE flips the picked row to status='running', locked_by=$2, locked_at=NOW() and then tx.Commit() (line 154) — FOR UPDATE SKIP LOCKED is released at commit, so no DB lock survives. The concurrency gate (lines 122-128) is NOT EXISTS(SELECT 1 FROM jobs j2 WHERE j2.concurrency_key=j.concurrency_key AND j2.status='running'), and ConcurrencyKey="pipeline:"+pipelineID is set at backend/internal/service/enqueuer.go:41 (finding cited enqueuer.go:41 — line matches exactly; only the package path differs, it's internal/service not internal/jobqueue). Complete/Fail/Reschedule (lines 186-237) every one gate on WHERE id=$1 AND locked_by=$2 AND status='running', so only the owning worker can clear the row; a crashed/OOM-killed/SIGKILLed worker is gone and never calls them, and Pool.handle()'s Reschedule path (worker.go:171) is bypassed entirely by a hard crash. locked_at is written (line 136) and nulled by Reschedule (line 228) but never read back against an age threshold. Grep + reads confirm no reaper exists anywhere: not in the Store interface (jobqueue.go:101-134), not in the worker Pool (worker.go), not in the boot path (jobqueue_boot.go wires Pool/Store/Listener/Dispatcher/Enqueuer but starts no sweeper, and PoolOptions has no reaper field). Net effect: one dead worker leaves a permanent 'running' row that blocks every future job for that pipeline key until manual SQL. stillOpen=true: the jobqueue stale-running/reaper concept is in NEITHER chain-recheck.md nor remediation-plan.md (the only adjacent items are Kaniko Job-TTL orphans B.2.3/B.7.8 and webhook-body OOM B.6.5 — different subsystems: K8s Jobs and HTTP body limits, not the durable jobqueue), and it is not on the known-false-positive list. Severity high holds: it is gated behind COOKER_JOBQUEUE_ENABLED (off by default) and the system is documented as single-replica-friendly, but a worker OOM/SIGKILL is a routine operational event and within a single replica it permanently wedges that pipeline's runs; default MaxAttempts=1 means the worker-side retry offers no relief either.

### 5. Job-queue-executed runs never write `heartbeat_at`, so the boot orphan sweep falsely reaps healthy in-flight durable runs

- **Severity / Dimension:** high / reliability
- **Location:** `backend/internal/service/jobqueue_runner.go:80-96`
- **Tracking:** new
- **Evidence:** JobQueueRunner.Handle calls executor.Execute directly (not RunCoordinator.Spawn), so no heartbeat goroutine runs; run.HeartbeatAt is only ever set by the coordinator (model/run.go:53-56), leaving heartbeat_at NULL for the whole durable run. SweepOrphans reaps `status='running' AND (heartbeat_at IS NULL OR ...)` (store/postgres/run.go:202-203), so any replica booting during a long durable run flips that healthy run to 'failed' — the exact rolling-deploy scenario the queue targets. The code comment at line 93 ("orphan sweep will eventually fail-out the row") inverts the real behavior.
- **Fix sketch:** In backend/internal/service/jobqueue_runner.go around lines 80-96, wrap the executor.Execute call with a heartbeat ticker that periodically calls store.Runs.UpdateHeartbeat(execCtx, run.ID, time.Now()) at heartbeatInterval — reuse the exact primitive RunCoordinator.heartbeatBestEffort uses (ideally extract a shared heartbeat-loop helper so the inline and durable paths share one implementation), so heartbeat_at is non-NULL for the whole durable run and SweepOrphans no longer reaps it.
- **Why it is real (verifier):** Reproduced in code. JobQueueRunner.Handle (backend/internal/service/jobqueue_runner.go:80-96) calls r.executor.Execute(execCtx, p, run) directly and never routes through server.RunCoordinator.Spawn/SpawnWithDeadline. Heartbeat writes live ONLY in RunCoordinator.heartbeatBestEffort (server/runs.go:136-143), driven by the ticker in SpawnWithDeadline (runs.go:97-118); Executor.Execute writes no heartbeat (the sole 'heartbeat' token in internal/service is an unrelated comment at executor.go:634). So a durable (job-queue) run keeps heartbeat_at NULL for its whole lifetime — the Runs.Update at jobqueue_runner.go:90 persists run.HeartbeatAt, which is nil. SweepOrphans (store/postgres/run.go:196-209) reaps `status='running' AND (heartbeat_at IS NULL OR heartbeat_at < NOW()-threshold)`, and the sweep runs on every boot (server.go:487, 60s default threshold). Therefore any replica booting during an in-flight durable run flips that healthy run to 'failed' with error 'orphaned: heartbeat stale at boot' — exactly the rolling-deploy survivability the durable queue is meant to provide. The line-93 comment is about the Update-failure path, not this mis-fire. Severity high: silent data-correctness corruption (healthy run reported failed, user must re-run) under the precise scenario the feature targets; scoped to operators who set COOKER_JOBQUEUE_ENABLED=true (off by default, jobqueue_boot.go:54) and run multi-replica, but for them every boot during an active durable run corrupts it. Still open: remediation-plan T6 + chain-recheck B.7.1 only cover the INLINE coordinator heartbeat (goroutine join, 30-min deadline) on runs.go, not the job-queue path that writes no heartbeat at all; jobqueue_runner is newer (tracking=new) and not on the known-false-positive list.

### 6. WebSocket handlers block forever on `h.register <- client` if the hub Run() loop has already exited

- **Severity / Dimension:** medium / concurrency
- **Location:** `backend/internal/server/wshub_logs.go:72`
- **Tracking:** BC-H3
- **Evidence:** `h.register <- client` is an unbuffered send into the hub's register channel; Run() (websocket.go:118-178) is the only receiver and returns when the backend Subscribe() channel closes on wsHub.Close(). On the non-graceful shutdown path (RunContext errCh branch + main.go:79 Close()) or a hijacked-WS upgrade that http.Server.Shutdown does not wait for, a handler stuck on this send hangs until process exit. Same pattern at websocket.go:228 and websocket.go:274. Listed HIGH (BC-H3) in docs/audits/2026-06-full-audit.md and NOT in that doc's Tier-1 DONE list.
- **Fix sketch:** In backend/internal/server/websocket.go add a hub `done chan struct{}` closed by Close()/when Run() returns, then replace the three blocking `h.register <- client` sends (wshub_logs.go:72, websocket.go:228, websocket.go:274) with `select { case h.register <- client: case <-h.done: conn.Close(); return }` — same non-blocking-select pattern already used in the broadcast path at websocket.go:152-156.
- **Why it is real (verifier):** Reproduced in code. `register` is an unbuffered channel (backend/internal/server/websocket.go:103 `register: make(chan *Client)`), and Run() at websocket.go:122 (`case client := <-h.register`) is the sole receiver. Run() exits at websocket.go:142-143 when the backend Subscribe() channel closes, which is triggered by wsHub.Close() (websocket.go:188-196). The three handler send sites — wshub_logs.go:72, websocket.go:228, websocket.go:274 — all do a blocking `h.register <- client` with no select/cancellation. A WS upgrade that hijacks the conn (http.Server.Shutdown does NOT wait for hijacked connections — documented Go behavior) and reaches line 72 after Run() has returned blocks that handler goroutine forever; same on the non-graceful errCh path (server.go:682) → main.go:79 srv.Close() → wsHub.Close() (server.go:781) → Run() returns, leaking any parked handler until process exit. This is BC-H3. NOT closed: the 2026-06-full-audit.md Tier-1 DONE list (line 144) enumerates BC-H1/H4/H5 but deliberately omits BC-H3; the Verified-fixed list (line 80) and chain-recheck.md / remediation-plan.md do not address this send-on-exit hang (remediation-plan only covers the unrelated startup launch-order reorder and the WS double-close sync.Once). NOT on the known-false-positive list — distinct from the excluded "wsHub launch order" item (that is the `go wsHub.Run()` start ordering, server.go:615, a startup concern). Severity: the finding self-rates medium and the audit rates HIGH; medium is defensible — impact is a leaked goroutine + FD + hijacked conn bounded to the shutdown window (delays clean exit, masked by process termination), not data loss and not a block on normal request serving.

### 8. CancelPipelineRun overwrites a terminal run status with no FSM/terminal guard and no optimistic-concurrency check

- **Severity / Dimension:** medium / correctness
- **Location:** `backend/internal/handler/pipeline.go:454`
- **Tracking:** new
- **Evidence:** Handler does `run.Status = model.RunStatusCancelled` then `h.Store.Runs.Update(...)` unconditionally; RunStore.Update is a blind `UPDATE pipeline_runs SET status=$2 ... WHERE id=$1` (store/postgres/run.go:159-163) with no status predicate. A run that already finished (success/failed) gets flipped to cancelled, corrupting history. Unlike the executor (which routes every write through runstate.TransitionRun and rejects terminal→X), the cancel handler bypasses the FSM and runstate.IsTerminal entirely.
- **Fix sketch:** In backend/internal/handler/pipeline.go CancelPipelineRun, before Update guard with the existing internal/runstate helper: if !runstate.CanTransitionRun(run.Status, runstate.EventCancel) { 409 Conflict }, then set run.Status = next from runstate.TransitionRun(...); optionally also add a status predicate (WHERE status NOT IN terminal) to RunStore.Update for defense-in-depth against the cancel-vs-finalize race.
- **Why it is real (verifier):** Reproduced in the cited code. backend/internal/handler/pipeline.go:454-455 sets run.Status = model.RunStatusCancelled and calls h.Store.Runs.Update(...) unconditionally, with no FSM gate and no IsTerminal/CanTransitionRun guard. The store's RunStore.Update (store/postgres/run.go:159-165) is a blind `UPDATE pipeline_runs SET status=$2 ... WHERE id=$1` with no status predicate and no version/optimistic-concurrency column, so a run already at success/failed gets flipped to cancelled, corrupting run history. Latent today because main.go always RunContext-then-Close.
- **Fix sketch:** In backend/internal/server/jobqueue_boot.go: store the Pool's cancel func + a done-channel on jobQueueDeps and have closeAll() cancel+wait (bounded by a per-call timeout, mirroring traceShutdown at server.go:773) to stop Pool BEFORE d.DB.Close(), making Server.Close() self-contained per the reverse-boot-order teardown the doc-comment already promises.
- **Why it is real (verifier):** Reproduced in code. closeAll (backend/internal/server/jobqueue_boot.go:35-45) closes only Listener and DB and never stops Pool; the Pool is the field set at line 121 and is drained solely by cancelling the ctx passed to Pool.Run in RunContext (server.go:627 -> worker.go:78-92 p.wg.Wait). Server.Close (server.go:786-788) calls s.jobQueue.closeAll() with no pool drain, and workers touch that same *sql.DB inside Store.Dequeue/Complete (jobqueue.NewPostgres(db); worker.go:103,128). So a direct Server.Close() without a preceding RunContext ctx-cancel would close db under in-flight workers. However this is latent only: main.go:78-79 always RunContext-then-Close, and RunContext's ctx.Done() path explicitly waits on jobPoolDone (the pool's wg.Wait completion) up to runDrainTimeout BEFORE returning (server.go:709-717), so the pool is already drained by the time Close() runs. The other closeAll caller is the cleanups slice (server.go:450), invoked only on New() construction failure, before Pool.Run is ever started — no in-flight workers. No real reachable caller misuses Close() today, and workers already tolerate Dequeue errors with a 2s backoff (worker.go:104-113) and recover handler panics, so blast radius is logged warnings / a stranded mid-flight job rather than a crash. Not mentioned in chain-recheck.md, remediation-plan.md, or W10-bug-and-chain-recheck.md (jobqueue boot post-dates the T-series recheck) and not on the known-false-positive list, so it remains open. Low severity / latent-hazard verdict is correct: Close() is not self-contained, it implicitly depends on the caller having drained the pool first.
